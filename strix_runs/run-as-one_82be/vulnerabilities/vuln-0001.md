# IDOR in Event Category Updates

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-09-23 01:54:16 UTC
**Target:** /workspace/run-as-one
**Endpoint:** /api/admin/events/[id]
**Method:** PUT
**CWE:** CWE-862
**CVSS:** 7.1
**Confidence:** High
**Fix Effort:** Trivial

## Description

The endpoint for updating an event (`PUT /api/admin/events/[id]`) does not verify that the categories being updated actually belong to the event. An attacker with edit access to any event can modify category details (name, distance, price, limits) across the entire platform by supplying target category IDs in their payload.

## Evidence

```typescript title=src/app/api/admin/events/[id]/route.ts startLineNumber=203 endLineNumber=215
      for (const cat of categories) {
        if (cat.id) {
          await prisma.category.update({
            where: { id: cat.id },
            data: {
              name: upperCaseForStorage(cat.name),
              distance: cat.distance || '',
              price: toCentavos(cat.price),
              imageUrl: cat.imageUrl || null,
              inclusions: asInclusions(cat.inclusions),
              slotLimit: asSlotLimit(cat.slotLimit),
            }
          });
```

## Impact

An attacker with `event:edit` access on a single event can modify the details (name, distance, price, slot limits, inclusions) of any category belonging to any other event or organization. This allows sabotage of competing events by changing their pricing, removing slot limits, or altering category inclusions.

## Counterevidence

The endpoint correctly restricts category deletions to the current event by using `eventId: id`. However, the subsequent loop that processes category updates directly calls `prisma.category.update` using only the provided `cat.id`. The lack of an `eventId: id` check in this update operation constitutes a concrete, bypassable authorization boundary.

## What Would Change This Severity

If category IDs are treated as highly unpredictable secrets not exposed anywhere, the likelihood of exploitation is reduced. However, category IDs are typically public in registration flows.

## Technical Analysis

In `src/app/api/admin/events/[id]/route.ts` (PUT handler), the application updates existing event categories using a loop over the provided `categories` array. For each category with an `id`, it executes a `prisma.category.update({ where: { id: cat.id }, data: { ... } })` call. Because the `where` clause only specifies `id` and does not enforce `eventId: id`, the query blindly updates any category in the database matching the provided ID, bypassing the event and organizer authorization checks performed earlier in the request.

## Proof of Concept

1. Log in as an Organizer or Event Manager with `event:edit` permissions for at least one event.
2. Identify the `id` of a category belonging to another organization's event (e.g., from the public registration page).
3. Send a `PUT` request to `/api/admin/events/<your_event_id>` to edit your own event.
4. In the JSON payload, include a `categories` array containing an object with the victim category's `id` along with modified values (e.g., `price: 1`).
5. The server updates the victim's category with the new values.

```python
import requests

# Assuming valid session cookie for an attacker with event:edit on event_id
session_cookie = '...'
attacker_event_id = 'attacker-event-123'
victim_category_id = 'victim-category-456'

headers = {'Cookie': f'session={session_cookie}', 'Content-Type': 'application/json'}
payload = {
    'title': 'Attacker Event',
    'date': '2025-01-01',
    'location': 'Test',
    'categories': [
        {
            'id': victim_category_id,
            'name': 'HACKED CATEGORY',
            'price': '1.00',
            'distance': '100K',
            'slotLimit': 1
        }
    ],
    'bankAccounts': []
}

requests.put(f'http://localhost:3000/api/admin/events/{attacker_event_id}', json=payload, headers=headers)
```

## Code Analysis

**Location 1:** `src/app/api/admin/events/[id]/route.ts` (lines 204-206)
  Use `updateMany` to securely restrict category updates to the current event

  **Suggested Fix:**
```diff
-         if (cat.id) {
-           await prisma.category.update({
-             where: { id: cat.id },
+         if (cat.id) {
+           await prisma.category.updateMany({
+             where: { id: cat.id, eventId: id },
```

## Remediation

Update the category loop in the `PUT` handler to use `prisma.category.updateMany` with `eventId: id` in the `where` clause. This ensures that the category being updated actually belongs to the event being edited.

## Fix Verification

I have verified that changing `update` to `updateMany` with `where: { id: cat.id, eventId: id }` securely limits the update to categories belonging to the event currently being edited. A malicious payload containing an external category ID will not match any rows in `updateMany` and will thus perform no operation, safely ignoring the IDOR attempt while preserving legitimate updates.

## Assumptions

Assumes the attacker is authenticated and holds a role with `event:edit` permissions on at least one event.
