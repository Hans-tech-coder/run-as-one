# Incomplete Logout / Failure to Invalidate JWT on Server Side

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-09-23 01:55:58 UTC
**Target:** Logout Endpoint (src/app/api/auth/logout/route.ts)
**CWE:** CWE-613
**CVSS:** 4.2
**Confidence:** High
**Fix Effort:** Low

## Description

The logout functionality only clears the `admin_token` cookie on the client side, but fails to invalidate the stateless JWT on the server side. An intercepted or stolen JWT can still be used after the user has explicitly logged out.

## Evidence

In `src/app/api/auth/logout/route.ts`:
```typescript
export async function POST() {
  await clearAuthCookie();
  return NextResponse.json({ success: true }, { status: 200 });
}
```
The route clears the cookie but does not utilize the existing `sessionsValidFrom` mechanism to invalidate the session in the database.

## Impact

If a user's JWT is stolen (e.g. via XSS, network interception, or local access), the attacker can continue to access the account until the token expires, even if the legitimate user attempts to terminate the session by logging out.

## Counterevidence

The JWT has a natural expiration time of 1 day, which limits the window of opportunity for an attacker. Furthermore, the application provides a "Sign out other devices" feature which does correctly update `sessionsValidFrom`.

## What Would Change This Severity

If the JWT expiration time was significantly longer (e.g., weeks or months), the impact would be much higher, raising the severity.

## Technical Analysis

The application uses stateless JWTs for session management, stored in an `httpOnly` cookie. The logout endpoint (`/api/auth/logout/route.ts`) simply calls `clearAuthCookie()`, which instructs the browser to delete the cookie. However, the JWT itself remains valid according to its cryptographic signature and expiration time (1 day).

Because the server does not track individual JWTs, it cannot natively invalidate a specific token. However, the application already implements a mechanism to invalidate all of a user's active tokens by updating the `sessionsValidFrom` timestamp in the database (used in `/api/admin/profile/sessions/route.ts`). Failing to update this timestamp during a normal logout means the token remains usable by anyone who manages to acquire it.

## Proof of Concept

1. Log into the application and extract the JWT from the `admin_token` cookie.
2. Log out of the application using the `/api/auth/logout` endpoint.
3. Attempt to access a protected route (e.g., `/api/admin/profile`) by manually providing the extracted JWT in the `admin_token` cookie.
4. The server accepts the token and processes the request successfully, proving the token was not invalidated.

```python
import requests

# 1. Provide a stolen JWT from a session that has already logged out
stolen_jwt = "eyJhb..."
cookies = {'admin_token': stolen_jwt}

# 2. Access a protected API route
response = requests.get('http://localhost:3000/api/admin/profile', cookies=cookies)

# 3. Observe the request succeeds (200 OK) instead of 401 Unauthorized
print(f"Status: {response.status_code}")
```

## Remediation

Update the logout route to invalidate the session on the server side. Since the application uses a stateless JWT without individual session IDs, the most straightforward fix using the existing schema is to update the user's `sessionsValidFrom` timestamp to the current time, identical to the "Sign out other devices" functionality. This ensures the JWT is rejected by `getActor()` on subsequent requests.

## Fix Verification

1. Applicability: The patch updates the logout route to use the existing `sessionsValidFrom` mechanism.
2. Security closure: A stolen JWT will be rejected by `getActor()` (via the `issuedBefore(session.iat, sessionsValidFrom)` check) after the user has logged out.
3. Bypass review: No alternative logout mechanisms exist that bypass this.
4. Preserved behavior: The user is still successfully logged out and the cookie is cleared.
5. Repository checks: The Prisma schema and actor functions are used identically to existing code.

## Assumptions

Assumes an attacker has intercepted, stolen, or otherwise gained access to a victim's active JWT token.
