# Empty Participants Array allows Free Ghost Registration Creation

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-09-23 01:55:26 UTC
**Target:** /workspace/run-as-one
**CWE:** CWE-20
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

The checkout routes do not validate that the `participants` array contains at least one runner. Submitting an empty array results in a subtotal of 0 and a platform fee of 0. The server considers this a free order, bypasses PayMongo entirely, and creates a PAID registration with no actual runners.

## Evidence

In `src/app/api/checkout/route.ts`, the code relies on validation functions like `participantEmailError`:

```typescript
export function participantEmailError(participants: unknown): string | undefined {
  if (!Array.isArray(participants)) return undefined;

  for (const [index, participant] of participants.entries()) {
    ...
```

If `participants` is `[]`, the loop is skipped and it returns `undefined`. Since the array is empty, `expectedSubtotal` is 0, and `platformFeeAfterDiscount` evaluates `Math.max(0, runners)` which is also 0. Consequently, `chargeableTotal` is 0. The order falls under the `isFreeOrder` path and creates a bogus registration directly into the database.

## Impact

An attacker can pollute the registration database with unlimited free, empty orders. This clutters the admin dashboard, interferes with analytics, and consumes some database resources, although it does not consume actual event slots since no runner records are created.

## Counterevidence

The application uses functions like `participantEmailError`, `participantBirthdateError`, and `participantGuardianError` to validate the `participants` array. However, each of these functions iterates over the array using a `for...of` loop or `.some()`. If the array is completely empty, the loops never execute and the functions return `undefined` (indicating no error). This allows an empty participants array to silently pass all validation steps.

## What Would Change This Severity

If the platform restricts automated API calls via WAF or CAPTCHA, this attack's mass exploitation is mitigated, but the logical flaw persists.

## Technical Analysis

All individual participant validation checks in the application (`participantEmailError`, `participantBirthdateError`, etc.) evaluate the array elements iteratively. If the array is empty, these checks gracefully return `undefined` assuming no issues. However, the checkout logic requires at least one participant to be meaningful. The absence of a check for `participants.length === 0` causes the pricing engine to calculate `0` totals, triggering the "free order" path (designed for fully discounted pacers) and injecting empty records into the database without payment.

## Proof of Concept

1. Send a POST request to `/api/checkout` with `"participants": []`.
2. Set `subtotal`, `deliveryFee`, `platformFee`, `transactionFee`, and `amount` to `0`.
3. Provide valid `customerEmail`, `customerName`, `eventId`, `consentGiven: true`, and `consentSignature`.
4. The server creates the order, bypasses PayMongo, and responds with a success URL, polluting the database with a ghost order.

```javascript
fetch('https://<target>/api/checkout', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },

    subtotal: 0,

    paymentMethod: "GCASH",

    consentSignature: "TEST CUSTOMER",
```

## Remediation

Verify that the `participants` array has a length greater than zero before performing any logic or calculations. Return a 400 Bad Request if it is empty.

## Fix Verification

Adding an explicit check for `!participants || participants.length === 0` directly in the API handlers securely guarantees that empty submissions are rejected with a 400 Bad Request before hitting pricing logic or Prisma creation, preventing the generation of junk orders.

## Assumptions

Assumes an attacker can directly invoke the `/api/checkout` or `/api/checkout/manual` API bypassing client-side validation that requires at least one participant.
