# Authentication Bypass in Middleware via Path Normalization (src/proxy.ts)

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-09-23 01:55:38 UTC
**Target:** Next.js Middleware (src/proxy.ts)
**CWE:** CWE-287
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The Next.js middleware (`src/proxy.ts`) uses `pathname.startsWith()` to whitelist public authentication routes. An attacker can bypass the middleware's authentication check by appending URL-encoded path traversal characters to a whitelisted path.

## Evidence

In `src/proxy.ts`:
```typescript
const PUBLIC_ADMIN_PATHS = ['/admin/login', '/admin/register', '/admin/invite'];

export default async function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname;
  if (PUBLIC_ADMIN_PATHS.some(path => pathname.startsWith(path))) {
    return NextResponse.next();
  }
```
If a request is made to `/admin/login/..%2f..%2fadmin%2fsettings`, `pathname.startsWith('/admin/login')` evaluates to true because Next.js `request.nextUrl.pathname` does not decode `%2f`. The middleware allows the request, but Next.js router then decodes the URL and resolves the path to `/admin/settings`, bypassing the middleware protection.

## Impact

An unauthenticated attacker can bypass the edge middleware authentication layer and reach protected admin routes. While the routes currently have redundant checks (`requireActor`), bypassing middleware exposes the underlying application logic and could lead to unauthorized access if a page misses the manual check.

## Counterevidence

The individual pages under `/admin` also check authentication using `requireActor()` or `requireTeamActor()`, so the application has defense-in-depth that mitigates the impact of this middleware bypass. In addition, the file is currently named `proxy.ts`, which Next.js ignores.

## What Would Change This Severity

If a protected admin page is missing the `requireActor()` check, this bypass would lead to full unauthorized access, increasing the severity to High.

## Technical Analysis

The middleware intended to protect the `/admin/*` routes (currently named `proxy.ts`) uses a vulnerable `startsWith` check to whitelist public paths:
```typescript
if (PUBLIC_ADMIN_PATHS.some(path => pathname.startsWith(path))) {
  return NextResponse.next();
}
```
Because `request.nextUrl.pathname` retains URL-encoded characters (like `%2f`), an attacker can craft a URI like `/admin/login/..%2f..%2fadmin%2fprotected` which satisfies the `startsWith('/admin/login')` condition. Once passed through the middleware, the Next.js router decodes the URL and normalizes the path traversal, routing the attacker directly to the protected page. This completely defeats the middleware's authentication enforcement. Additionally, the file is named `proxy.ts` instead of `middleware.ts`, causing Next.js to ignore it entirely.

## Proof of Concept

1. Intercept a request to the application.
2. Modify the URL to `/admin/login/..%2f..%2fadmin%2fsettings`.
3. Send the request without any authentication cookies.
4. The middleware evaluates `pathname.startsWith('/admin/login')` as true and skips checking the `admin_token` cookie, forwarding the request to the Next.js router which resolves it to `/admin/settings`.

```python
import requests

url = "http://localhost:3000/admin/login/..%2f..%2fadmin%2fsettings"
# The request will bypass proxy.ts middleware because it starts with /admin/login
response = requests.get(url, allow_redirects=False)
print(f"Status: {response.status_code}")
```

## Remediation

1. Rename `proxy.ts` to `middleware.ts` so Next.js actually loads the middleware.
2. Replace `startsWith` with exact path matching, or parse the normalized pathname safely. Next.js provides `request.nextUrl.pathname` which can be strictly checked against the `PUBLIC_ADMIN_PATHS` array.

## Assumptions

Assumes the middleware is active (e.g. named `middleware.ts`). An attacker needs to know a valid protected path to traverse to.
