# Insecure Direct Object Reference on Category ID allows Payment Bypass

**ID:** vuln-0003
**Severity:** HIGH
**Found:** 2026-09-23 01:55:03 UTC
**Target:** /workspace/run-as-one
**CWE:** CWE-639
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The checkout routes (`/api/checkout` and `/api/checkout/manual`) fail to validate whether the `categoryId` provided for a participant actually belongs to the specified `eventId`. If an attacker supplies a `categoryId` belonging to a different event, the price calculation defaults to 0, allowing them to register while paying only the minimal administrative fee (or 0 if waived).

## Evidence

In `src/lib/shirt-size.ts`, the `runnerPrices` function calculates the cost of each participant:

```typescript
export function runnerPrices(...) {
  return participants.map(p => {
    const category = (categories ?? []).find(c => c.id === p.categoryId);
    return (
      (category ? category.price : 0) +
      shirtSizeUpchargeFor(p, categories, upchargePerRunner)
    );
  });
}
```

The `categories` parameter contains only the categories belonging to the current event. If an attacker submits a `categoryId` from a completely different event, `category` is undefined, and the price defaults to `0`. 

Since the `Runner` model's foreign key only validates that the `categoryId` exists in the `Category` table, Prisma successfully inserts the record. The attacker's `expectedSubtotal` becomes 0, and they bypass paying the actual registration fee, only paying the base platform fee (e.g., 60 PHP).

## Impact

An attacker can bypass paying the race entry fee (which could be thousands of PHP) and register for high-value events while only paying the negligible platform fee. This represents a significant financial loss and business logic bypass.

## Counterevidence

I checked if `reserveSlots` validates the category ID against the event. `reserveSlots` simply filters out categories that do not have `slotLimit > 0`. If the category ID is not in `event.categories`, it is entirely ignored and no slots are reserved. Prisma's database schema guarantees that the `categoryId` is a valid category globally, but does not enforce that it belongs to the target event. Therefore, the order calculation proceeds with a `0` subtotal.

## What Would Change This Severity

If platform fees are also somehow bypassed or zeroed out, the attacker could register entirely for free without providing any payment.

## Technical Analysis

The system correctly retrieves the `event` and its associated `categories` from the database. However, it passes the user-supplied `participants` directly to price calculation functions like `subtotalWithUpcharge`. Within `runnerPrices`, the code searches for the user's `categoryId` in the event's categories. If `Array.prototype.find()` returns undefined, the code defaults the price to `0` instead of failing. Prisma's relational schema validates that the `categoryId` exists in the `Category` table, but does not enforce a multi-level link verifying that `Category.eventId` equals `Registration.eventId`. Thus, providing a valid category from a different event perfectly exploits this logic flaw.

## Proof of Concept

1. Identify an event you want to register for and its `eventId`.
2. Find the `categoryId` of a valid category belonging to a *different* event (e.g., by inspecting another event page).
3. Send a POST request to `/api/checkout` with your registration payload, but set `categoryId` to the one from the different event.
4. The server calculates the `subtotal` as 0. Set the `subtotal` field in the payload to `0`, and set `amount` to just the platform fee (e.g., `6000` for 60 PHP).
5. The checkout succeeds, you are directed to PayMongo to pay only the 60 PHP fee, and you successfully register for the target event.

## Remediation

In both checkout routes, iterate over the `participants` array and explicitly assert that every `categoryId` is present in the `event.categories` array fetched from the database. Reject the request with a 400 Bad Request if any category is invalid.

## Fix Verification

I reviewed the changes and confirmed that explicit validation of the `categoryId` against the `event.categories` list securely prevents the vulnerability. The patch is applied at the entry point of both checkout routes, ensuring that an invalid or cross-event category immediately fails the transaction before any pricing or database logic is executed. Valid categories provided by legitimate users continue to work correctly.

## Assumptions

Assumes the attacker can select a valid category ID belonging to a different event (or from a previous event) by inspecting other events' categories.
