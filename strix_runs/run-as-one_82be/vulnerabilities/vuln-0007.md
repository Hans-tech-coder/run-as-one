# Negative Transaction Fee Allows Payment Bypass

**ID:** vuln-0007
**Severity:** HIGH
**Found:** 2026-09-23 01:56:26 UTC
**Target:** /workspace/run-as-one
**CWE:** CWE-602
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The checkout routes blindly trust the `transactionFee` (or `transactionFeeCents`) value provided by the client when calculating the total order amount. Because the application does not validate that the transaction fee is non-negative, an attacker can submit a negative transaction fee to offset the cost of the event. When choosing an e-wallet like GCash or PayMaya, this manipulated, vastly reduced total amount is passed directly to the PayMongo Payment Intents API.

## Evidence

In `src/app/api/checkout/route.ts`, the total is validated as follows:

```typescript title=src/app/api/checkout/route.ts startLineNumber=207 endLineNumber=209
    const expectedTransactionFee = free ? 0 : transactionFeeCents;
    const expectedTotal = chargeable + expectedTransactionFee;
    if (amountCents !== expectedTotal || transactionFeeCents !== expectedTransactionFee) {
```

If a client sends `chargeable = 5000` (50 PHP) and `transactionFeeCents = -3000` (-30 PHP):
1. `expectedTransactionFee` evaluates to `-3000`.
2. `expectedTotal` evaluates to `5000 + (-3000) = 2000` (20 PHP).
3. The check `transactionFeeCents !== expectedTransactionFee` is `-3000 !== -3000`, which is false (validation passes).
4. The check `amountCents !== expectedTotal` is `2000 !== 2000`, which is false (validation passes).

Later, in the GCash / PayMaya logic:

```typescript title=src/app/api/checkout/route.ts startLineNumber=394 endLineNumber=407
          data: {
            attributes: {
              amount: amountCents,
```

The system sends the manipulated `amountCents` (2000 / 20 PHP) to PayMongo. The attacker successfully pays 20 PHP for a 50 PHP order, bypassing the expected costs.

## Impact

An attacker can arbitrarily reduce the cost of their registration to the minimum payment amount accepted by PayMongo (usually 20 PHP for e-wallets), completely bypassing the actual race entry costs while still receiving a fully paid and confirmed registration.

## Counterevidence

The code correctly recomputes the `subtotal`, `deliveryFee`, and `platformFee` from the database. However, the comments explicitly state: `"The transaction fee is still the client's own figure... so this pins the total against it rather than re-deriving it."` As a result, the server natively trusts `transactionFeeCents`. If it's negative, the total `amountCents` is reduced. PayMongo Payment Intents API processes whatever `amount` it is handed, and the application's webhook marks the order PAID based on ID mapping without verifying if the final paid amount covers the original required `chargeable` amount.

## What Would Change This Severity

If the organizers rely exclusively on Credit Cards (Checkout Sessions API) rather than e-wallets, the impact might be slightly reduced because PayMongo's Checkout Session API may calculate the total sum from `lineItems` independently. However, e-wallets currently use the Payment Intents API, directly exposing this flaw.

## Technical Analysis

The vulnerability arises from Server-Side Trust of Client-Calculated Data (CWE-602). The server correctly recalculates all items forming the `chargeable` total, but explicitly allows the client to dictate the `transactionFee`. Since the application does not validate that `transactionFee >= 0`, an attacker can provide a negative fee. This negative value mathematically offsets the `chargeable` amount in the `expectedTotal = chargeable + expectedTransactionFee` calculation. When `storedPaymentMethod` is an e-wallet (GCASH or PAYMAYA), the application uses the Payment Intents API and directly sets `attributes.amount: amountCents`. The server effectively charges the attacker's chosen reduced total.

## Proof of Concept

1. Start the registration flow and select GCash or PayMaya as the payment method.
2. Intercept the final POST request to `/api/checkout`.
3. Set `transactionFee` (or `transactionFeeCents`) to a negative value that offsets the `subtotal`, leaving the final `amount` (or `amountCents`) at the PayMongo minimum (e.g., 2000 for 20 PHP).
4. For example, if `subtotal` is 5000, set `transactionFee` to -3000 and `amount` to 2000.
5. Forward the request. The server accepts the negative fee, generates a PayMongo intent for 20 PHP, and marks the registration as `PAID` upon successful payment of the 20 PHP.

## Remediation

Validate that `transactionFeeCents` is greater than or equal to 0 before calculating `expectedTotal`. If the client submits a negative transaction fee, reject the request. Additionally, verify in the webhook handler that the amount paid matches the registration's total expected amount, not just relying on the status change.

## Fix Verification

I reviewed the `transactionFeeCents` handling in the codebase. By enforcing a validation check that `transactionFeeCents < 0` immediately fails the request with a 409 status, it is mathematically impossible for an attacker to reduce `amountCents` below the securely server-computed `chargeableTotal`. Valid checkouts will continue to work since expected transaction fees are always positive.

## Assumptions

Assumes the attacker selects a payment method that utilizes the Payment Intents API (e.g., GCASH or PAYMAYA), where the total amount is explicitly provided rather than being derived by PayMongo from line items.
